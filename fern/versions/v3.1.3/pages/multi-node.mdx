## About Multi-Node NIM Deployment

[Multi-Node NIM Deployment](https://docs.nvidia.com/nim/large-language-models/latest/multi-node-deployment.html)
addresses the problem of deploying massive LLMs that cannot fit on a single GPU or need to use older GPUs.
This feature enables the distribution of model weights and computation across several interconnected nodes.

NIM Operator supports deploying multi-node NIM on Kubernetes using [LeaderWorkerSets (LWS)](https://github.com/kubernetes-sigs/lws), as supported by NIM Helm Chart.

NIM Operator supports multi-node deployments for both NIM version 2.0+ and earlier NIM versions.
The configuration shape differs between the two: NIM 2.0+ uses the `spec.multiNode.ray` block on the NIMService, while earlier NIM versions use `spec.multiNode.mpi`.
The two blocks are mutually exclusive on a single NIMService.
Refer to [NIM Service Configuration Reference](/service#nim-service-configuration-reference) for the full list of multi-node configuration fields.

For more information on multi-node deployments, refer to [Multi-Node Deployment for NVIDIA NIM for LLMs](https://docs.nvidia.com/nim/large-language-models/latest/multi-node-deployment.html) in the *NVIDIA NIM for LLMs* documentation.

<Note>
Upgrade and ingress of multi-node NIM are supported.
However, auto-scaling, DRA, and Multi-LLM NIM are not yet supported for multi-node configurations.

</Note>

<Tabs>
  <Tab title="NIM 2.0+" language="nim-2">
Before deploying a multi-node NIM, ensure the following:

- A Kubernetes cluster with GPU nodes, where each node has the same number and type of GPUs.

- Sufficient GPU resources across the nodes to satisfy the tensor parallelism × pipeline parallelism (TP × PP) requirement of your NIM.

  Find the number of GPUs required for your desired model in [Support Matrix for NVIDIA NIM for LLMs: LLMs](https://docs.nvidia.com/nim/large-language-models/latest/reference/support-matrix.html#llms).

- The [LeaderWorkerSet (LWS)](https://github.com/kubernetes-sigs/lws) CRD installed on the cluster:

  ```console
  $ kubectl apply --server-side -f https://github.com/kubernetes-sigs/lws/releases/latest/download/manifests.yaml
  ```

  <Note>
  LWS version 0.6.2 or later is required.

  </Note>

- Shared storage (recommended): A PVC with `ReadWriteMany` access mode, `hostPath`, or NFS, so the leader downloads the model once and shares it with the workers.

- High-speed networking (recommended): InfiniBand or [RDMA over Converged Ethernet (RoCE)](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-516/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/) for optimal NCCL performance.

  For IPoIB with Mellanox NICs, refer to the [NVIDIA Network Operator documentation](https://docs.nvidia.com/networking/display/kubernetes2540/getting-started-kubernetes.html#network-operator-deployment-with-an-ip-over-infiniband-ipoib-network) for installation and configuration.

- An NGC API key stored as a Kubernetes secret:

  ```console
  $ kubectl create secret generic ngc-api --from-literal=NGC_API_KEY=<your-key>
  ```

For more information, refer to [Prerequisites](https://docs.nvidia.com/nim/large-language-models/latest/deployment/multi-node-deployment.html#prerequisites) in the *NVIDIA NIM for LLMs* documentation.

  </Tab>

      1.       Define NICClusterPolicy.

         After Network Operator is installed, create a NICClusterPolicy CR to install the DOCA Driver (part of MLNX_OFED),

         <Note>
         If MOFED/DOCA driver is already pre-installed on the host, then remove the `ofedDriver` section in the below CR sample.

         ```yaml
         metadata:

         spec:

             image: doca-driver
             repository: nvcr.io/nvidia/mellanox
             version: 25.04-0.6.1.0-2
             forcePrecompiled: false
             imagePullSecrets: []
             terminationGracePeriodSeconds: 300
             startupProbe:
               initialDelaySeconds: 10
               periodSeconds: 20
             livenessProbe:
               initialDelaySeconds: 30
               periodSeconds: 30
             readinessProbe:
               initialDelaySeconds: 10
               periodSeconds: 30

               autoUpgrade: true
               maxParallelUpgrades: 1

             config: |
               {
                 "configList": [
                   {
                     "resourceName": "rdma_shared_device_a",
                     "rdmaHcaMax": 63,
                     "selectors": {
                       "vendors": [],
                       "deviceIDs": [],
                       "drivers": [],
                       "ifNames": ["ibs1f0"],
                       "linkTypes": []
                     }
                   }
                 ]
               }
           secondaryNetwork:
             cniPlugins:
               image: plugins
               repository: ghcr.io/k8snetworkplumbingwg
               version: v1.6.2-update.1
               imagePullSecrets: []
             multus:
               image: multus-cni
               repository: ghcr.io/k8snetworkplumbingwg
               version: v4.1.0
               imagePullSecrets: []
             ipoib:
               image: ipoib-cni
         ```

<Anchor id="define-ipoib"></Anchor>

      1.       Define an IP over IB Multus Network.

         Use the sample CR below to define a IP over IB network:

         ```yaml
         apiVersion: mellanox.com/v1alpha1
         kind: IPoIBNetwork
         metadata:
           name: example-ipoibnetwork
         spec:
           networkNamespace: "default"
           master: "ibs1f0"
           ipam: |
             {
               "type": "whereabouts",
               "datastore": "kubernetes",
               "kubernetes": {
                 "kubeconfig": "/etc/cni/net.d/whereabouts.d/whereabouts.kubeconfig"
               },
               "range": "192.168.5.225/28",
               "exclude": [
               "192.168.6.229/30",
               "192.168.6.236/32"
               ],
               "log_file" : "/var/log/whereabouts.log",
               "log_level" : "info",
               "gateway": "192.168.6.1"
             }
         ```

         -          Configure `.spec.networkNamespace` to the namespace of the Kubernetes resources that will use the multus network. (It is the namespace that NetworkAttachmentDefinition will be created.)

         -          Configure `.spec.master` to the IB interface you wish to enslave by the multus network on the host node.

         -          Ensure the IP Cidr under `.spec.ipam` is not conflicting with the existing network (for example, default CNI podCidr and other networks).

         Once the above CR is created, a Multus NetworkAttachmentDefintion will be created for consumption in the namespace specified in `.spec.networkNamespace`.

<Anchor id="create-cache-nim-2"></Anchor>

1. Create a cache for the NIM.

   1.    Create a file, such as `nimcache.yaml`, with contents like the following:

      ```yaml
      apiVersion: apps.nvidia.com/v1alpha1
      kind: NIMCache
      metadata:
        name: multi-node-nimcache
        namespace: nim-service
      spec:
        source:
          ngc:
            modelPuller: nvcr.io/nim/openai/gpt-oss-20b:2.0.3
            pullSecret: ngc-secret
            authSecret: ngc-api-secret
            model:
        storage:
          pvc:
            create: true
            storageClass: ''
            size: "100Gi"
            volumeAccessMode: ReadWriteMany
      ```

      Set `spec.storage.pvc.storageClass` to a storage class that supports dynamic provisioning and `ReadWriteMany` access.
Leaving `spec.source.ngc.model` empty lets the Operator perform automatic profile selection for the available GPUs.

   1.    Apply the manifest:

      ```console
      $ kubectl apply -n nim-service -f nimcache.yaml
      ```

   <Note>
   The NIM Cache job might fail due to various reasons, such as from network issues.
NIM Operator automatically retries 5 times to download the model.
In such scenarios, you might see some cache jobs in error states.

   </Note>

<Anchor id="create-service-nim-2"></Anchor>

1. Create a NIM Service that uses the NIM 2.0+ multi-node configuration.

   1.    Create a file, such as `nimservice.yaml`, with contents like the following:

      ```yaml
      apiVersion: apps.nvidia.com/v1alpha1
      kind: NIMService
      metadata:
        name: multi-node-nimservice
        namespace: nim-service
      spec:
        image:
          repository: nvcr.io/nim/openai/gpt-oss-20b
          tag: "2.0.3"
          pullPolicy: IfNotPresent
          pullSecrets:
            - ngc-secret
        authSecret: ngc-api-secret
        storage:
          nimCache:
            name: multi-node-nimcache
        replicas: 1
        resources:
          limits:
            nvidia.com/gpu: 1
          requests:
            nvidia.com/gpu: 1
        expose:
          service:
            type: ClusterIP
            port: 8000
        multiNode:
          parallelism:
            pipeline: 2
            tensor: 1
          ray:
            rayPort: 6379
      ```

      The `spec.multiNode.ray` block selects the NIM 2.0+ multi-node configuration.
`rayPort` defaults to `6379`.
Set it explicitly only if you need to override the default.

   1.    Apply the manifest:

      ```console
      $ kubectl create -f nimservice.yaml -n nim-service
      ```

## Troubleshooting

This section explains some common troubleshooting steps to identify issues with Multi-Node configurations.

- If the system comes with Intel IB devices, the kernel module `irdma` is likely loaded. This will conflict with the Mellanox OFED driver, causing the below failure when installing MOFED:

  ```output
  Function: generate_ofed_modules_blacklist Unloading ib_uverbs [FAILED] rmmod: ERROR: Module ib_uverbs is in use by: irdma [16-Jul-25_16:25:49] Command "/etc/init.d/openibd restart" failed with exit code: 1 [16-Jul-25_16:25:49] Remove blacklisted mofed modules file from host
  ```

  To resolve the conflict, remove the `irdma` module and blacklist it:

  ```console
  $ sudo rmmod irdma
  $ echo "blacklist irdma" | sudo tee /etc/modprobe.d/blacklist-irdma.conf
  ```

  Then reboot the node.

- Ensure the LeaderWorkerSet controller is deployed onto the cluster before NIM Operator.
If LeaderWorkerSet controller is deployed after NIM Operator, restart NIM Operator

- Ensure that no existing GPU workloads are running on the nodes before deploying GPU Operator.

- Ensure the NFS volume is accessible and has enough space, and its CSI driver is correctly set up.

- Multi-node NIM without RoCE can experience frequent restart on the LWS leader and worker pods due to model shard loading timeout. NCCL with Infiniband connection is highly recommended

- If using infiniband:

  -   Ensure network operator is [deployed with IP over Infiniband network](https://docs.nvidia.com/networking/display/kubernetes2540/getting-started-kubernetes.html#network-operator-deployment-with-an-ip-over-infiniband-ipoib-network).

  -   Refer to [`config/samples/nim/serving/advanced/multi-node/multi-node-nimservice-rdma.yaml`](https://github.com/NVIDIA/k8s-nim-operator/blob/release-3.0/config/samples/nim/serving/advanced/multi-node/multi-node-nimservice-rdma.yaml) in the GitHub repository for a sample multi-node nim over IB network.

- If the NIM Cache job failed while downloading the model, a new cache job is created.

  The NIM Cache job might fail due to various reasons, such as from network issues.
NIM Operator automatically retries 5 times to download the model.
In such scenarios, you might see some cache jobs in error states.

### Logs and Messages to Gather

- NIM container logs, such as PyTorch, SGLang, and NCCL, can be viewed from the LWS leader pods, for example:

  ```console
  $ kubectl logs deepseek-r1-lws-0
  ```

- Kubernetes deployment logs can be found in the NIM operator using the following command:

  ```console
  $ kubectl logs -l app.kubernetes.io/instance=nim-operator
  ```

- Additional information can be found by describing the NIM Service using the following command:

  ```console
  $ kubectl describe nimservice
  ```
