## About NIM Services

A NIM service is a Kubernetes custom resource, `nimservices.apps.nvidia.com`.
The NIM Service spec remains the same across non-LLM NIM, LLM-Specific NIM, and Multi-LLM NIM, except the repository name as shown in the following examples.
You create and delete NIM service resources to manage NVIDIA NIM microservices.

Refer to the sample manifests below for examples for different deployment scenarios. For full information on available fields, see the [NIM Service Configuration Reference](#nim-service-configuration-reference).

<td>

Specifies the name of a generic secret that contains the credential used to download model weights.
Most NIMs use `NGC_API_KEY`.
NVIDIA NeMo Retriever Embedding NIM 2.0.0 uses `HF_TOKEN` with its default Hugging Face model download provider, or `NGC_API_KEY` when `NIM_MODEL_DOWNLOAD_PROVIDER=ngc`.
Learn more about [image pull secrets](/image-pull-secrets).

This field is optional.
If you omit this field, the Operator does not inject the `NGC_API_KEY` environment variable into the NIM pod.
If you set this field, the Operator references the secret as optional, so the pod starts even if the secret or its `NGC_API_KEY` key does not exist.
Omit the field only for [air-gapped deployments](/air-gap#serving-a-pre-cached-model-without-an-ngc-api-key) that serve a pre-cached model and never download from NGC.

### Scaling a NIM Service to Zero

A horizontal pod autoscaler can scale a NIM service to zero replicas when the NIM service has no demand, and scale the NIM service back up when demand returns.
This configuration frees the GPUs that the NIM service uses while the NIM service is idle.

Scaling to zero has the following requirements:

- The Kubernetes `HPAScaleToZero` feature gate.
Kubernetes v1.37 and later enable the feature gate by default.
On earlier Kubernetes versions, set `HPAScaleToZero=true` on the kube-apiserver and the kube-controller-manager.

- `spec.scale.hpa.minReplicas` set to `0` and at least one `External` or `Object` metric in `spec.scale.hpa.metrics`.
The horizontal pod autoscaler scales up from zero replicas only by using `External` and `Object` metrics.

- A demand metric that a component outside the NIM pods publishes, such as a gateway or a request queue.
The NIM for LLMs service metrics, such as `gpu_cache_usage_perc`, come from the NIM pods, so these metrics are not available while the NIM service has zero replicas.

- A metrics adapter that serves the demand metric through the Kubernetes external metrics API, `external.metrics.k8s.io`.
The horizontal pod autoscaler reads `External` metrics only from the external metrics API.
If only Prometheus collects the demand metric, the horizontal pod autoscaler cannot read the demand metric and cannot scale the NIM service up from zero replicas.
For example, add an external rule for the demand metric to the Prometheus Adapter configuration, and keep the metric labels that `spec.scale.hpa.metrics[].external.metric.selector` matches, such as `model`.
Refer to [Observability](/observability) for installing Prometheus Adapter.

The following partial manifest scales a NIM service between zero and one replica based on an external metric named `nim_pending_requests`:

```yaml
spec:
  scale:
    enabled: true
    hpa:
      minReplicas: 0
      maxReplicas: 1
      metrics:
      - type: External
        external:
          metric:
            name: nim_pending_requests
            selector:
              matchLabels:
                model: meta-llama3-8b-instruct
          target:
            type: Value
            value: "1"
      behavior:
        scaleDown:
          stabilizationWindowSeconds: 60
```

When the metric reports no demand, the horizontal pod autoscaler scales the NIM service deployment to zero replicas and sets the `ScaledToZero` condition to `True`.
When the metric reports demand, the horizontal pod autoscaler scales the deployment to one replica, and the NIM microservice starts and loads the model before the NIM microservice serves requests.

A request to the NIM service does not wake the NIM service.
While the NIM service has zero replicas, requests to the NIM service fail.
In production, send requests through a gateway or queue that publishes the demand metric and buffers or retries requests until the NIM microservice is ready.

Let the horizontal pod autoscaler scale the deployment to zero.
If you scale the deployment to zero manually, the horizontal pod autoscaler stops scaling the deployment.

To check the horizontal pod autoscaler conditions, run the following command:

```console
$ kubectl describe hpa -n nim-service meta-llama3-8b-instruct
```

The following example creates a priority class named `nim-high-priority`:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: nim-high-priority
value: 1000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "Priority class for NIM workloads."
```

Add the priority class name to your `NIMService` manifest:

```yaml
spec:
  priorityClassName: nim-high-priority
```
